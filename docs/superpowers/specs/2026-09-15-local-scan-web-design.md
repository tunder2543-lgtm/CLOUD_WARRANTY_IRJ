# เว็บ Local สำหรับสแกนและอัปโหลดออเดอร์รายเดือน

วันที่ออกแบบ: 2026-09-15

## เป้าหมาย

เพิ่มหน้าเว็บที่รันเฉพาะบนเครื่องผู้ใช้สำหรับควบคุมขั้นตอนใน `bot/` โดยยังใช้กติกาเดิมทั้งหมดของ `scan.py`, `merge_dates.py`, `apply.py` และ `verify.py` ผู้ใช้เลือกตำแหน่งโฟลเดอร์ได้ทั้งแบบเลือกโฟลเดอร์เดือนโดยตรง หรือเลือกโฟลเดอร์ปีแล้วเลือกเดือน จากนั้นสแกน ตรวจผล ให้ Codex อ่านวันที่และเลขบัตรจากภาพ crop ยืนยันการอัปโหลด และดูรายงานได้จากหน้าเว็บ

หน้าเว็บใหม่นี้แยกจาก `index.html` และระบบออเดอร์หลัก ไม่เปลี่ยนพฤติกรรมของหน้าเว็บเดิม

## ขอบเขต

### รวมในรุ่นนี้

- เว็บเซิร์ฟเวอร์ Python ที่ฟังเฉพาะ `127.0.0.1`
- หน้าเว็บภาษาไทยสำหรับเลือกโฟลเดอร์ สแกน ตรวจความพร้อม อัปโหลด และตรวจผล
- รองรับการเลือกโฟลเดอร์เดือนโดยตรง
- รองรับการเลือกโฟลเดอร์ปี แล้วแสดงรายการโฟลเดอร์เดือนที่พบ
- จำพาธที่ใช้ล่าสุดในไฟล์ตั้งค่าภายใน `bot/`
- แสดง log และความคืบหน้าของงานที่กำลังรัน
- แสดงผลสแกนแยกตามสถานะ พร้อมภาพ crop ของบัตร
- ตรวจจับการเปลี่ยนแปลงของ `plan.json` หลัง Codex เติมวันที่และเลขบัตร
- แสดงตัวอย่างรายการที่จะอัปโหลดและขอการยืนยันก่อนเขียนข้อมูลจริง
- ใช้กลไกข้ามออเดอร์ซ้ำ, pre-flight, retry, state และ verify เดิม
- แสดงรายงานหลังตรวจสอบเสร็จ

### ไม่รวมในรุ่นนี้

- การเรียก OpenAI API หรือบริการ OCR จากเว็บโดยตรง
- การเปิดเว็บจากเครื่องอื่นในเครือข่าย
- การแก้ข้อมูลออเดอร์หลักจากหน้าควบคุมนี้
- การเปลี่ยนกติกาจำแนกบัตรหรือกติกาอัปโหลดเดิม
- การรันหลายเดือนพร้อมกัน

## แนวทางสถาปัตยกรรม

ใช้ Flask เป็น HTTP server และมี frontend แบบ HTML/CSS/JavaScript ธรรมดาเพื่อให้เข้ากับโครงสร้างโปรเจกต์เดิม ฝั่ง server จะเรียกฟังก์ชัน Python จากโมดูลเดิมโดยตรงหรือเรียกผ่าน service wrapper ที่บางและทดสอบได้ หลีกเลี่ยงการทำสำเนากติกาธุรกิจใน JavaScript

ส่วนประกอบหลัก:

1. `bot/web_app.py` เป็น entry point ของ Local server, API และการเสิร์ฟหน้าเว็บ
2. `bot/web_service.py` จัดการสถานะงาน, lock, การเลือก root, การรัน scan/apply/verify และการอ่านผล
3. `bot/web/` เก็บ HTML, CSS และ JavaScript ของหน้าควบคุม
4. `bot/web_settings.json` เก็บพาธล่าสุดและโหมดเลือกล่าสุด ไฟล์นี้เป็นข้อมูลเฉพาะเครื่องและต้องไม่ commit
5. ไฟล์งานจริงยังใช้ `bot/work/plan.json`, `state.json`, `crops/` และ `report.md` เหมือนเดิม เพื่อให้ใช้คำสั่ง CLI เดิมและ Codex ร่วมกันได้

เซิร์ฟเวอร์จะอนุญาตงานที่เปลี่ยนสถานะได้ครั้งละหนึ่งงานด้วย process-local lock หากมี scan, upload หรือ verify กำลังทำงาน API เริ่มงานใหม่จะตอบปฏิเสธพร้อมข้อความที่อ่านเข้าใจได้

## การเลือกโฟลเดอร์

หน้าเว็บมีสองโหมด:

### เลือกโฟลเดอร์เดือน

ผู้ใช้เลือกโฟลเดอร์ เช่น `G:\My Drive\ใบรับประกัน\ไฟล์ใบรับประกันใหม่\ปี2569\9.กันยายน` ระบบตรวจว่าพาธมีอยู่ อ่านหมายเลขและชื่อเดือนจากชื่อโฟลเดอร์ แล้วแสดงค่าที่ตรวจพบก่อนเริ่มสแกน

### เลือกโฟลเดอร์ปี

ผู้ใช้เลือกโฟลเดอร์ เช่น `...\ปี2569` ระบบค้นหาเฉพาะโฟลเดอร์ลูกโดยตรงที่มีรูปแบบเดือน เช่น `8.สิงหาคม` และ `9.กันยายน` แล้วแสดงเป็นรายการให้เลือก ระบบจะไม่ค้นลึกทั่วไดรฟ์

ช่องพาธแก้ไขด้วยการพิมพ์หรือวางได้เสมอ ปุ่มเลือกโฟลเดอร์จะเรียก native Windows folder dialog จาก backend เฉพาะเมื่อ server รันแบบ local interactive หาก dialog เปิดไม่ได้ ผู้ใช้ยังใช้ช่องพาธได้ และหน้าเว็บจะแสดงคำแนะนำชัดเจน

## ลำดับการทำงาน

1. ผู้ใช้เปิด Local server และเข้า dashboard ใน browser
2. ผู้ใช้เลือกโฟลเดอร์เดือนโดยตรง หรือเลือกโฟลเดอร์ปีและเดือน
3. ระบบตรวจพาธและแสดงเดือนที่จะใช้เป็นประเภทงาน
4. ผู้ใช้กด “สแกนเดือนนี้”
5. ระบบรันตรรกะจาก `scan.py` สร้าง `plan.json` และ crop โดยแสดง log ระหว่างทำงาน
6. หน้าเว็บแสดงสรุปและรายการตามสถานะ รวมถึงออเดอร์ที่พบว่ามีอยู่ในฐานข้อมูลแล้ว
7. หากยังขาดวันที่ หน้าเว็บแสดงสถานะ “รอ Codex อ่านบัตร” พร้อมข้อความคำสั่ง เช่น `อ่านและทำเดือน 9 ต่อ`
8. ผู้ใช้ส่งคำสั่งนั้นใน Codex จากนั้น Codex อ่าน crop และใช้ `merge_dates.py` เติมผลลง `plan.json`
9. หน้าเว็บ poll สถานะไฟล์เป็นช่วงสั้น ๆ และอัปเดตเป็น “พร้อมตรวจสอบ” เมื่อรายการพร้อม
10. ผู้ใช้เปิดหน้าตรวจสอบก่อนอัปโหลด เห็นจำนวนออเดอร์ จำนวนรูป วันที่ รายการข้าม และคำเตือน
11. ผู้ใช้กดยืนยัน “อัปโหลดรายการที่พร้อม” ระบบรันกลไกจาก `apply.py` โดยใช้ค่าเริ่มต้นที่ปลอดภัย: ไม่ replace และเปิด pre-flight
12. ระบบรัน `verify.py` หลัง apply เสร็จ และแสดงรายงานบนหน้าเว็บ

การเปลี่ยน root ไปเดือนอื่นยังใช้กลไก archive ของ `scan.py` เดิม เพื่อไม่ให้ผลเดือนก่อนถูกทับโดยไม่มีสำเนา

## API ภายในเครื่อง

API ใช้ JSON ยกเว้นไฟล์ภาพ crop:

- `GET /api/status` คืนสถานะงานปัจจุบัน สรุป plan และเวลาที่ไฟล์เปลี่ยนล่าสุด
- `POST /api/folder-dialog` เปิดตัวเลือกโฟลเดอร์บน Windows และคืนพาธที่เลือก
- `POST /api/discover-months` รับพาธโฟลเดอร์ปีและคืนเดือนที่พบ
- `POST /api/scan` ตรวจพาธและเริ่ม scan เบื้องหลัง
- `GET /api/jobs/current` คืนสถานะและ log ที่เพิ่มขึ้นของงานปัจจุบัน
- `GET /api/plan` คืนข้อมูลที่จำเป็นต่อหน้าตรวจสอบ โดยไม่เปิดเผย secret จาก `js/config.js`
- `GET /api/crops/<folder>` ส่งภาพ crop เฉพาะไฟล์ที่อ้างอิงอยู่ใต้ crop directory
- `POST /api/apply` เริ่มอัปโหลดหลังตรวจว่ามีรายการพร้อมและผู้ใช้ส่งค่ายืนยัน
- `POST /api/verify` รันตรวจสอบซ้ำด้วยตนเอง
- `GET /api/report` คืนรายงานล่าสุดในรูปที่ frontend แสดงได้อย่างปลอดภัย

ทุก endpoint ที่รับพาธหรือชื่อไฟล์ต้อง resolve และตรวจขอบเขต ป้องกัน path traversal และไม่ส่ง Supabase key หรือค่า config ลับไปยัง browser

## การใช้โค้ดเดิม

แยกฟังก์ชันแกนกลางออกจาก `main()` เท่าที่จำเป็น เพื่อให้ CLI และเว็บเรียก implementation เดียวกัน:

- `scan.py` มีฟังก์ชันรัน scan ที่รับ root/options/progress callback และคืน plan summary
- `apply.py` มีฟังก์ชัน preview และฟังก์ชัน apply ที่รับ options/progress callback
- `verify.py` มีฟังก์ชัน verify ที่คืน structured result พร้อมเขียนรายงานเดิม
- CLI เดิมยังทำงานได้และมี argument เหมือนเดิม

การจัดลำดับภาพยังเป็นบัตรด้านหลัง → บัตรด้านหน้า → รูปที่เหลือ และจำนวนรูปสูงสุดยังอ้างอิง `MAX_IMGS` เดิม

## หน้าตาและการใช้งาน

หน้าจอใช้รูปแบบโต๊ะควบคุมงานเอกสาร ไม่ใช่ dashboard แบบการ์ดสำเร็จรูป:

- แถบหัวแสดงชื่อเครื่องมือ เดือนที่เลือก และสถานะ server
- แผงเลือกแหล่งข้อมูลอยู่ด้านซ้าย พร้อมสวิตช์สองโหมดและพาธที่อ่านได้ชัด
- แผงสถานะงานด้านขวาแสดงขั้นปัจจุบันและ log ล่าสุด
- ตารางเต็มความกว้างด้านล่างแสดงโฟลเดอร์ วันที่ จำนวนรูป สถานะ และเหตุผลที่ข้าม
- แถวที่ต้องตรวจเปิดดู crop ได้โดยไม่ออกจากหน้า
- ปุ่มอัปโหลดใช้สีเน้นเพียงจุดเดียวและแสดงจำนวนรายการที่จะเขียนอย่างชัดเจน
- รองรับหน้าจอแคบ, keyboard focus, reduced motion และ contrast ที่อ่านได้

ข้อความทุกจุดใช้ภาษาไทยและระบุการแก้ปัญหา เช่น “ไม่พบโฟลเดอร์ — ตรวจอักษรไดรฟ์หรือรอ Google Drive เชื่อมต่อ” แทนข้อความ error ทั่วไป

## สถานะและข้อผิดพลาด

สถานะงานหลักคือ `idle`, `scanning`, `waiting_for_dates`, `ready_to_upload`, `uploading`, `verifying`, `complete` และ `failed`

- ข้อผิดพลาดระดับรายการใช้สถานะเดิมใน plan เช่น `no_cert`, `ambiguous`, `date_failed` และ `card_mismatch`
- ข้อผิดพลาดระดับงานไม่ลบ plan หรือ state เดิม ผู้ใช้ดู log และลองใหม่ได้
- การปิด browser ไม่หยุดงาน Python ที่กำลังรัน เมื่อเปิดหน้าใหม่ระบบอ่านสถานะกลับมาได้ตราบใดที่ process server ยังทำงาน
- ปุ่ม apply ปิดใช้งานเมื่อไม่มีรายการที่มี `status=ready` และ `date_iso`
- ค่า `replace` ปิดไว้ในรุ่นแรกเพื่อลดความเสี่ยงการเขียนทับ หากต้องการ replace ให้ใช้ CLI เดิม
- หาก verify พบปัญหา งานจบในสถานะที่แสดงคำเตือน ไม่รายงานว่าเสร็จสมบูรณ์

## ความปลอดภัย

- bind เฉพาะ `127.0.0.1` และไม่เปิดรับจาก LAN
- ตรวจ `Origin`/host สำหรับ request ที่เปลี่ยนข้อมูล
- ไม่ส่งค่าจาก `SUPABASE_KEY` ไป frontend หรือ log
- apply ต้องมี token ยืนยันที่ server สร้างจาก preview ล่าสุด เพื่อป้องกันการกดจากข้อมูลเก่า
- ตรวจว่าพาธ crop ที่ร้องขออยู่ภายใน `CROP_DIR`
- ไม่ลบไฟล์ต้นฉบับของผู้ใช้
- ไม่เปลี่ยนหรือเขียนไฟล์ในโฟลเดอร์รูปต้นทาง

## การทดสอบ

### Unit tests

- ตรวจการค้นหาเดือนจากโฟลเดอร์ปีและการเรียงเดือน 1–12
- ตรวจ validation ของพาธและการป้องกัน path traversal
- ตรวจ mapping สถานะจาก plan เป็นสถานะหน้าเว็บ
- ตรวจ preview ว่าข้าม state ที่เสร็จแล้วและเลขออเดอร์ที่มีในฐานข้อมูล
- ตรวจว่า apply ใช้ลำดับรูปเดิมและไม่เปิด replace
- ตรวจการปิดบัง secret ใน API และ log

### Integration tests

- ใช้ temporary directory จำลองโฟลเดอร์ปี/เดือนและไฟล์ภาพ
- เรียก scan ผ่าน API แล้วตรวจว่า job status, log และ plan summary เปลี่ยนถูกต้อง
- จำลอง plan ที่ Codex merge แล้วตรวจว่า UI backend เปลี่ยนจากรอวันที่เป็นพร้อมอัปโหลด
- mock Supabase สำหรับ preview/apply/verify เพื่อไม่เขียนข้อมูลจริงระหว่างทดสอบ
- ตรวจว่าเริ่มงานที่สองขณะงานแรกทำงานอยู่ไม่ได้

### Manual verification

- เปิด server บน Windows และเลือกโฟลเดอร์ด้วย dialog
- ทดสอบทั้งโหมดโฟลเดอร์เดือนและโหมดโฟลเดอร์ปี
- สแกนแบบจำกัดรายการกับสำเนาข้อมูลทดสอบ
- ตรวจภาพ crop และลำดับภาพใน preview
- ใช้ dry-run ก่อนทดสอบอัปโหลดจริงหนึ่งโฟลเดอร์
- ตรวจผลในฐานข้อมูลและเปิดรูป cover จาก URL หลัง verify

## เกณฑ์สำเร็จ

- ผู้ใช้เลือกตำแหน่งโฟลเดอร์ได้ทั้งสองรูปแบบโดยไม่แก้ environment variable
- การสแกนจากเว็บให้ผลเท่ากับการรัน CLI ด้วย root เดียวกัน
- Codex สามารถเติมผลวันที่ผ่านไฟล์งานเดิม และหน้าเว็บตรวจพบโดยไม่ต้อง restart
- ระบบไม่อัปโหลดออเดอร์ที่มีอยู่แล้วและไม่เขียนทับโดยปริยาย
- รูปบัตรด้านหลังเป็นรูปแรกของทุกออเดอร์ที่อัปโหลด
- ผู้ใช้เห็นผลสำเร็จ รายการข้าม คำเตือน และข้อผิดพลาดจากหน้าเว็บ
- CLI เดิมยังใช้งานได้
